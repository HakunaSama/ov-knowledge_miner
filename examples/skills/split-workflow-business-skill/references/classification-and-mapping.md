# 分类与映射规则

## 四类边界

拆分时先问这条规则在回答什么问题。

| 问题 | 归属 | 典型内容 |
| --- | --- | --- |
| 系统必须怎样执行且不能被用户破坏？ | `SKILL.md` | 阶段顺序、接口、检查点、审计产物、安全、恢复、校验 |
| 用户希望产出什么知识、面向谁、怎样表达？ | `USER_PROFILE.md` | 目标、受众、选材、原子性、术语、证据偏好、语言、文风 |
| 用户是否有一套更完整的原子企业知识政策？ | `USER_PROFILE_ATOMIC_ENTERPRISE_KNOWLEDGE.md` | 知识对象模型、合并拆分、页面内容、关系、增量维护、技术资料偏好 |
| 文件应放在哪里、允许什么类型和主视图结构？ | `OKF_CONFIG.yaml` | `main_view` 路径层级、页面角色、frontmatter、导航和标准 Markdown 链接 |

不要把 OKF 当成第四个要新建的拆分结果；它是已有的独立契约，只需原样保留。

## 典型判断示例

| 原规则 | 去向 | 原因 |
| --- | --- | --- |
| 必须先提交完整 source coverage，再产生候选知识 | `SKILL.md` | 执行顺序与硬门禁 |
| 每一页至少有一个真实来源并通过 provenance 校验 | `SKILL.md` | 不可放宽的正确性约束 |
| 优先提炼可复用的规则、决策和方法 | 当前 Profile | 用户可调整的选材偏好 |
| 面向了解业务但未读原文的新同事 | 当前 Profile | 受众偏好 |
| 同一主题跨文档合并，互不相关的主题拆开 | 原子知识 Profile；若为硬校验则固定部分留在 `SKILL.md` | 业务原子化策略与平台底线需要按子句拆分 |
| `knowledge/procedure/.../{filename}.md` 使用 procedure 页面角色 | `OKF_CONFIG.yaml` | 单一主视图的路径和角色契约 |
| `_mining/evidence-ledger.json` 必须包含哪些字段 | `SKILL.md` | 中间产物协议 |
| 使用简洁中文，先给结论 | 当前 Profile | 写作偏好 |

## 混合内容的处理

一条原文可能同时包含业务目标和实现方法，例如：

> 为保证每份文件都被利用，先调用覆盖率接口，再优先提取稳定、可复用的业务规则。

拆成两条：

- “先调用覆盖率接口”进入 `SKILL.md`；
- “优先提取稳定、可复用的业务规则”进入当前 Profile。

不要整句在两边各复制一次，否则以后用户修改 Profile 时仍可能间接改变流程。

## 边界难题

### 质量要求还是业务偏好

用“是否允许用户安全地关闭它”判断：

- 关闭后会破坏正确性、可追溯性、协议兼容或安全：留在 `SKILL.md`；
- 关闭后只会改变选材、详略、读者体验或表达方式：放入 Profile。

### 默认 Profile 还是候选 Profile

- 拆分前实际生效的业务规则应进入 `USER_PROFILE.md`，否则拆分本身改变行为。
- 额外输入的完整原子企业知识政策进入候选 Profile，并明确默认不加载。
- 如果系统原本已经使用完整原子知识政策，则它应成为 `USER_PROFILE.md` 的有效内容；候选文件只是保存一个可切换版本，不能靠文件名擅自改变激活状态。

### 规则需要两处出现

仅允许边界声明或简短摘要重复。例如两个 Profile 都应说明“不能覆盖固定流程”。详细定义必须只有一个权威位置，并通过链接或加载说明引用它。

## 可追踪映射模板

```markdown
| ID | 原文件:位置 | 规则摘要 | 分类 | 目标位置 | 处理 | 验证 |
| --- | --- | --- | --- | --- | --- | --- |
| R-001 | OLD_SKILL.md:42 | 覆盖所有上传源 | 固定流程 | SKILL.md/Source coverage | 原义迁移 | 通过 |
| R-002 | OLD_SKILL.md:80 | 面向知识型新手 | 业务偏好 | USER_PROFILE.md/Audience | 精简改写 | 通过 |
```

处理字段可用：`原义迁移`、`拆句迁移`、`去重并入`、`保留在 OKF`、`删除纯说明重复`。对删除项写明理由。

## 完成标准

- 每条有效规则都可从原位置追踪到唯一权威位置。
- 没有流程实现细节从 Profile 反向控制固定 Skill。
- 默认行为不因文件拆分而无意变化。
- 替换 Profile 不需要修改固定 Skill。
- OpenViking 或底层实现升级时，业务 Profile 可以继续复用；流程适配集中发生在固定 Skill 或外部适配层。
